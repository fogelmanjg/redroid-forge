# Troubleshooting — problemas que la gente realmente tuvo

**Idiomas:** [English](TROUBLESHOOTING.md) | Español

Esta página solo cubre problemas que alguien realmente tuvo usando redroid-forge — no es una lista
especulativa de todo lo que podría fallar en teoría. Si te pasa algo que no está acá, abrí un issue
(ver `CONTRIBUTING.md`); una vez entendido, se agrega acá para que la próxima persona no tenga que
debuggearlo de cero.

Ver también [`docs/SCRCPY-TIPS.md`](SCRCPY-TIPS.es.md) para problemas específicos de conectar con
el cliente `scrcpy` real desde una terminal (audio, códec de video, bitrate) — esta página es sobre
la app en sí (instancias, el visor web integrado, recursos).

| Síntoma | Por qué | Solución |
|---|---|---|
| Una instancia informa muchísima más RAM que su límite asignado (por ejemplo `dumpsys meminfo` o `/proc/meminfo` adentro de la instancia muestra toda la RAM del host, no el límite real) | Android solo ve el límite real del cgroup gracias a un workaround (ver el comentario propio de `meminfoFix.js`): el propio init de Android monta un `/proc/meminfo` falso al bootear, disparado por un archivo `.rc`. Encontrado en vivo (17/11/2026): si el permiso de ese `.rc` en disco se degrada a escritura de grupo/otros, el init de Android lo rechaza en silencio ("insecure file") y el bind nunca pasa — la instancia sigue informando toda la RAM del host aunque el límite del cgroup sí se esté aplicando por debajo. | Arreglado de forma defensiva desde el build en la rama hacia `1.0.0` posterior al 17/11/2026 (la copia siempre fuerza el permiso correcto, sin depender del archivo fuente en disco). Una instancia **creada o recreada antes de ese fix** puede seguir con una copia rota — un simple restart **no** lo vuelve a aplicar (el `.rc` solo se (re)instala al crear/recrear, ver el comentario arriba de `installRcTrigger` en `meminfoFix.js`); recrear la instancia sí. |
| En el visor "expandida" (pantalla completa), escribir con el teclado físico no hace nada — solo responde tocar el teclado en pantalla de Android | Es así a propósito, no es un bug: el campo de texto oculto que captura el tipeo físico solo se enfoca si clickeás primero el botón **⌨** (pasale el mouse o enfocalo para ver un recordatorio). Aun así, solo se manda el texto plano ya confirmado — Backspace, Enter, Tab y las flechas nunca se mandan (sin IME/composición propia, ver las decisiones de diseño de "expandida" en `ROADMAP.md` Fase 11). | Clickeá **⌨** antes de escribir. Para Backspace/Enter/flechas, usá el propio teclado en pantalla de Android (se ve en el video, tocalo directo) — todavía no hay reenvío de esas teclas específicas. |
| Usando una app de scrcpy de terceros en Android (ej. `ScrcpyForAndroid`/miuzarte) desde un celular o tablet para mirar una instancia de redroid-forge: pantalla negra al conectar, o la app se cierra sola al desconectar | Bugs conocidos del decoder de esa app de terceros específica al hablar con una instancia de redroid (rastreados hasta su propio código fuente — ver las notas internas del proyecto); no es algo que redroid-forge controle o pueda arreglar desde este lado. | Usar el visor web integrado **"expandida"** desde el propio navegador de la tablet en vez de esa app (mismo dispositivo, sin apps extra, sin los bugs de decoder de ese APK en particular). |
| Una instancia se reinicia por completo mientras se reproduce un video (preview de Play Store, un video publicitario, cualquier reproducción tipo `VideoView`/`ExoPlayer`) | **Causa raíz confirmada (17/11/2026, `herotale` + una instancia de dev descartable).** No es orientación ni resolución — ambas se probaron y descartaron directamente (un video vertical colgó una instancia vertical; dos buffers que colgaron tenían tamaños distintos, [1280,720] y [768,1280]). El disparador es **qué formato de color negocia el decoder del video**: confirmado vía logs de `CCodec`, contenido decodificado por hardware que negocia `color-format` `2135033992` (`COLOR_FormatYUV420Flexible`, resuelve a NV12/formato propio del vendor) nunca cuelga; contenido que cae a decode por software con `color-format` `19` (`COLOR_FormatYUV420Planar`, resuelve a `HAL_PIXEL_FORMAT_YV12`) siempre cuelga. Una traza en vivo con ptrace sobre una instancia de dev descartable (nunca sobre prod) encontró el paso exacto que falla: no es la función de `libEGL_mesa.so` que adivina el layout YCbCr del lado del gralloc (esa acepta el buffer sin problema) — es el import real a GPU vía GL/EGL que viene justo después. En el constructor `GaneshBackendTexture::GaneshBackendTexture` de `surfaceflinger`, confirmado en vivo: 5 texturas RGBA comunes de UI (720×1280) se importan bien a la GPU una tras otra, y después el buffer YV12 del frame de video (768×1280, el ancho real de 720px alineado a 32 bytes) devuelve su flag de "éxito" del import GL en `0`, lo que dispara directo el `__android_log_assert("Failed to create a valid texture...")` que mata todo el proceso — confirmado en `/data/tombstones`, `format:842094169` = YV12. Como `surfaceflinger` es el único compositor del sistema, esta única falla se lleva todo Android, no solo la app. Reportado upstream, hallazgos completos: [remote-android/redroid-doc#942](https://github.com/remote-android/redroid-doc/issues/942). | **Todavía no hay fix, pero el disparador y el paso exacto que falla ya se conocen**: evitar contenido/configuraciones que fuercen decode de video por software con salida planar legacy (codecs viejos como XviD/MPEG4 ASP; algunas fuentes H.264 baseline, incluyendo ciertos videos de preview de Play Store). El contenido decodificado por hardware con codecs modernos (HEVC confirmado funcionando) no se ve afectado. |
| El `system_server` de una instancia se cae (`DeadSystemException` en `dumpsys dropbox --print system_server_crash`, precedido de `Looper: Slow dispatch/delivery took 4xxms` en su hilo principal) — puede pasar incluso antes de instalar ninguna app/juego, solo por el arranque normal (GMS, package manager y media provider inicializando todos a la vez) | Encontrado en vivo (17/11/2026, `herotale`, pinneada a un solo hilo del cpuset): `cpusetCpus` es pura **afinidad** de CPU (confirmado en `dockerRuntime.js` — solo se usa `CpusetCpus`, nunca `CpuQuota`/`CpuShares`/`NanoCpus`), no un tope de rendimiento. El propio `system_server` lanza un montón de threads (pool de binder, GC, inicialización de servicios) que necesitan paralelismo real durante picos de carga — pinneados a un solo hilo de hardware, esos threads se pisan entre sí aunque ningún otro contenedor esté compitiendo por nada. | **Nunca asignes un solo cpu en `cpusetCpus` — dos como mínimo.** No necesitan ser exclusivos: dos instancias pueden compartir el mismo par (ej. `cifi`/`cifi-nuevo`, ambas en `"7,15"`) y cada una sigue teniendo margen real para picos de dos hilos, porque el kernel reparte ese pool de forma dinámica — no es "un hilo para cada una". Un par libre/dedicado para una sola instancia también funciona (ej. `"4,12"`). Se aplica con `POST /api/instances/:id/resources` y `{"cpusetCpus": "..."}` — un update en vivo de Docker, sin recrear la instancia. |

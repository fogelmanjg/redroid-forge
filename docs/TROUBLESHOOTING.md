# Troubleshooting — problems people actually hit

**Languages:** English | [Español](TROUBLESHOOTING.es.md)

This page only covers problems someone actually ran into while using redroid-forge — not a
speculative list of everything that could theoretically go wrong. If you hit something that isn't
here, open an issue (see `CONTRIBUTING.md`); once it's understood, it gets added here so the next
person doesn't have to debug it from scratch.

See also [`docs/SCRCPY-TIPS.md`](SCRCPY-TIPS.md) for problems specific to connecting with the
real `scrcpy` client from a terminal (audio, video codec, bit rate) — this page is about the app
itself (instances, the built-in web viewer, resources).

| Symptom | Why | Fix |
|---|---|---|
| An instance reports way more RAM than its cap (e.g. `dumpsys meminfo` or `/proc/meminfo` inside the instance shows the host's full RAM, not the memory limit it was given) | Android only sees the real cgroup limit through a workaround (see `meminfoFix.js`'s own comment): a fake `/proc/meminfo` gets bound in by Android's own init at boot, triggered by a `.rc` file. Found for real (17/11/2026): if that `.rc`'s permissions on disk ever drift to group/other-writable, Android's init silently refuses to process it ("insecure file") and the bind never happens — the instance keeps reporting the host's full RAM even though the cgroup limit is genuinely enforced underneath. | Fixed defensively since the `1.0.0`-track build after 17/11/2026 (the copy is always forced back to the right permission, regardless of the source file on disk). An instance **created or recreated before that fix** can still be stuck on a broken copy — a plain restart does **not** re-apply it (the `.rc` is only (re)installed on create/recreate, see the comment above `installRcTrigger` in `meminfoFix.js`); recreating the instance does. |
| In the expanded viewer (full-screen), typing on the physical keyboard does nothing — only tapping Android's own on-screen keyboard works | By design, not a bug: the hidden text field that captures physical typing only gets focus when you click the **⌨** button first (hover/focus it for a reminder). Even then, only plain committed text is forwarded — Backspace, Enter, Tab and the arrow keys are never sent (no IME/composition handling, see the expanded viewer design decisions in `ROADMAP.md` Phase 11). | Click **⌨** before typing. For Backspace/Enter/arrows, use Android's own on-screen keyboard (visible in the video, tap it directly) or the physical keyboard shortcuts scrcpy itself doesn't need here — there is no key-event passthrough for those yet. |
| Using a third-party scrcpy Android app (e.g. `ScrcpyForAndroid`/miuzarte) from a phone or tablet to view a redroid-forge instance: black screen on connect, or the app closes unexpectedly on disconnect | Known decoder bugs inside that specific third-party app when it talks to a redroid instance (traced into its own source — see the project's internal notes); not something redroid-forge controls or can fix from this side. | Use the built-in **expanded viewer** from the tablet's own browser instead (same device, no extra app, no decoder bugs specific to that APK). |
| An instance reboots completely while a video plays (Play Store preview, a video ad, any `VideoView`/`ExoPlayer`-style playback) | **Root cause confirmed (17/11/2026, `herotale` + a disposable dev instance).** Not orientation, not resolution — both were tested and ruled out directly (a portrait video crashed a portrait instance; two different crashing buffers were different sizes, [1280,720] and [768,1280]). The trigger is **which pixel format the video decoder negotiates**: confirmed via `CCodec` logcat output across several real clips, content decoded in hardware that negotiates `color-format` `2135033992` (`COLOR_FormatYUV420Flexible`, resolves to NV12/vendor-private) never crashes; content that falls back to software decode with `color-format` `19` (`COLOR_FormatYUV420Planar`, resolves to `HAL_PIXEL_FORMAT_YV12`) always crashes. Live ptrace tracing on a disposable dev instance (never on prod) pinned down the *exact* failing step: it is not the gralloc-side YCbCr-layout guesser in `libEGL_mesa.so` (that one accepts the buffer fine) — it's the actual GL/EGL texture import right after it. In `surfaceflinger`'s `GaneshBackendTexture::GaneshBackendTexture` constructor, confirmed live: 5 ordinary RGBA UI-layer textures (720×1280) import to the GPU successfully in a row, then the one YV12 video-frame buffer (768×1280, the 32-byte-aligned stride of the real 720px width) comes back with its GL-import "success" flag at `0`, which immediately triggers `__android_log_assert("Failed to create a valid texture...")` and kills the whole process — confirmed in `/data/tombstones`, `format:842094169` = YV12. Since `surfaceflinger` is the system's only compositor, this one failure takes down all of Android, not just the one app. Reported upstream, full findings: [remote-android/redroid-doc#942](https://github.com/remote-android/redroid-doc/issues/942). | **No fix yet, but the trigger and exact failing step are known**: avoid content/configurations that force software video decode with legacy planar output (older codecs like XviD/MPEG4 ASP; some H.264 baseline sources, including certain Play Store preview videos). Content decoded in hardware with modern codecs (HEVC confirmed working) is unaffected. |
| An instance's `system_server` crashes (`DeadSystemException` in `dumpsys dropbox --print system_server_crash`, preceded by `Looper: Slow dispatch/delivery took 4xxms` on its main thread) — can happen even before any app/game is installed, just from normal boot churn (GMS, package manager, media provider all initializing at once) | Found for real (17/11/2026, `herotale`, pinned to a single cpuset thread): `cpusetCpus` is pure CPU **affinity** (confirmed in `dockerRuntime.js` — only `CpusetCpus` is ever set, no `CpuQuota`/`CpuShares`/`NanoCpus`), not a throughput cap. `system_server` on its own spawns many threads (binder pool, GC, service init) that want genuine parallelism during bursts — pinned to exactly one hardware thread, those threads starve each other even with zero contention from any other container. | **Never assign a single cpu in `cpusetCpus` — two, minimum.** They don't need to be exclusive: two instances can share the same pair (e.g. `cifi`/`cifi-nuevo` both on `"7,15"`) and still each get real two-way burst headroom, because the kernel hands out the pool dynamically — it's not "one thread each." A single free/dedicated pair works too (e.g. `"4,12"`). Apply via `POST /api/instances/:id/resources` with `{"cpusetCpus": "..."}` — a live Docker update, no recreate needed. |
